# Visual consistency audit (A3), 2026-11-21

Scope: `ui/theme`, `ui/components` (incl. `map/`), `ui/motion`, and the screens under `scaffold/screens/{onboarding,planning,underway,settings,home,login,places}`. Read-only, from code and CLAUDE.md section 6 (no Figma access, so "Figma says" claims below are inferred from KDoc and previews).

Paths are relative to `app/src/main/java/com/example/hackapp/`. **Defect** = wrong or unreadable output; **Taste** = works, but inconsistent or weaker than it could be. P0 = fix before any demo, P1 = fix this sprint, P2 = when touching the file.

## Summary

Token hygiene is good. Outside `ui/theme/` there is one colour literal (`ui/motion/Motion.kt:107`, `Color.White`), no `fontSize`/`.sp`, and no ad-hoc `TextStyle`/`FontWeight`; every text uses `MaterialTheme.typography.*`. The problems are in **how** the tokens are combined: a hero-only component placed on a light page, a progress track that reads backwards, map states that look the same, and card or button variants that differ for no reason.

## Light vs dark check

- Dark scheme pairs checked (primary/onPrimary, primaryContainer pairs, error, surface/onSurface, assumed `onSurfaceVariant` #D7C2BA on #19120E about 11:1): all pass AA. The assumed dark `canvas` #19120E = dark surface, fine.
- Hero, heroCard and card are the same in both modes by design. `AppColors.card` (always white) is not used anywhere at the moment; if someone uses it with `onSurface` text in dark mode, the text will be light on white. Consider removing `card` or documenting "use with `HackappPalette.Ink`".
- `ScreenLogin` forces `HackappTheme(darkTheme = true)` on the hero background (`ScreenLogin.kt:73`): consistent with its KDoc, and the outlined text fields and primary button read well there.
- Stop-type palettes: text #151515 on every container in all three modes is at least about 9:1. Only the dot use (item 14) is weak.

## Decisions (team-lead, 2026-11-21)

Nothing is implemented yet. The fixes listed above go into the Phase 2 plan after the five audits are consolidated.

- **D1 `secondaryContainer` stays #5D002C** (Figma variable; the theme mirrors Figma). Rule: **Figma's secondaryContainer is a dark burgundy; do not rely on M3 defaults that use it.** Components set explicit roles: StepProgress track `surfaceContainerHigh`; tonal buttons `primaryContainer`/`onPrimaryContainer` (pass `ButtonDefaults.filledTonalButtonColors(...)`); map Previewed `primaryContainer`. Watch for: `FilledTonalButton`, `NavigationBar` indicator, `FilterChip`/`InputChip` selected container (check), `SegmentedButton` active container, `Badge`. Changing the colour in Figma is raised with the user by team-lead.
- **D2 Page buttons** in `BottomActions` are full width (`fillMaxWidth()`), and all page-button variants use **`labelLarge`**. Text buttons used as tertiary actions can stay content width. ux-designer agreed, with these constraints (from UX #24):
  - Labels may wrap to 2 lines: no `maxLines = 1` and no fixed `height`. Use only `heightIn(min = …)` (56 for page buttons, 40 for small, never under 48 touch target) so the button grows at 200% font.
  - Pin at most 1 primary and 1 secondary action. On Leg, "Google Maps directions" moves into the scrolling content (`ScreensUnderway.kt:112`).
  - The visible label is the accessible name: no `contentDescription` override on text buttons.
- **D3 Page background = `AppColors.canvas`**, with content cards on `AppColors.card` (white). Underway and Welcome keep `hero`. Previews keep `PreviewDefaults.CANVAS`. Consequences:
  - Item 12 is solved by D3 (white card on canvas).
  - Item 13 (cool canvas vs warm cards) stays open as a taste note; Figma decides.
  - **Open defect created by D3:** `card` is white in **both** modes (`Color.kt:144`, "mode-independent"), while dark `canvas` is #19120E. A white card in dark mode with theme text (`onSurface` #EAE1DD) gives about 1.2:1. Either the dark `card` becomes a dark surface (suggest `surfaceContainer` #251E1B), or everything placed on `card` must use fixed ink (`HackappPalette.Ink`) and not the theme `onSurface`, which also breaks M3 children such as text fields and chips. Recommendation: dark `card` = #251E1B (an assumption like the dark `canvas`, to be confirmed in Figma).
  - `HackappPage` default `containerColor` moves from `surface` to `canvas`; `ModalBottomSheet` and top app bar colours have to be checked against canvas.
- **D5 Dark `card` = #251E1B** (= dark `surfaceContainer`); light stays #FFFFFF. In `Color.kt` the `DarkAppColors` copy gets `card = Color(0xFF251E1B)` with a comment "assumed, not in Figma", like the dark `canvas`. Fixes the white-card-in-dark-mode defect created by D3. Phase 2.
  - Suggested CLAUDE.md 6.1 edit (for team-lead): "Assumed (not in Figma): dark canvas `#19120E`, dark onSurfaceVariant `#D7C2BA`" becomes "Assumed (not in Figma): dark canvas `#19120E`, dark card `#251E1B` (= surfaceContainer), dark onSurfaceVariant `#D7C2BA`". Also in 6.1, "card" in the AppColors list can read "card (white light / `#251E1B` dark)".
- **D4 Corner rule:** hero or feature cards 32 (`ExtraLarge`), content cards and callouts 24 (`Large`), list items and option cards 16 (`Medium`). Padding: 20 / 16 / 16 (list item content 16 h, 12 v).

## Design-system decisions requested (team-lead) (answered above)
1. **secondaryContainer** (item 4): keep it = hero burgundy (Figma as implemented), or change it to a light container so M3 defaults look right.
2. **Page buttons** (items 6, 8): full width in `BottomActions`, one label style (`titleMedium` or `labelLarge`).
3. **Page background** (items 12, 13): screens on `surface` (current) or on `canvas`; previews must match.
4. **Corner rule** (item 9): 32 hero / 24 content / 16 list item.
